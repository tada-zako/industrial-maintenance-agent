# 开发目标文档（批次三）：前端、接口与项目验收

## 1. 本批次结论

本项目实现一个面向工业空压机运维 Demo 的 Vue 前端看板。

前端不重新实现 Agent 聊天系统，而是展示 Hermes Dashboard 不适合展示的业务内容，并提供进入 Hermes 对话页面的入口。

前端重点展示：

- 设备清单和运行状态；
- 需要关注的设备问题；
- 故障和维修草案；
- Agent 多工具调用流程；
- 知识图谱和维修案例证据；
- 外部资料导入结果。

系统提供最低限度的业务 CRUD，但不实现复杂后台管理系统。

## 2. 前端技术方案

### 2.1 技术栈

| 技术 | 用途 |
|---|---|
| Vue 3 | 前端页面和组件开发 |
| TypeScript | 前端类型定义 |
| Vite | 前端开发和构建 |
| Vue Router | 页面路由 |
| Element Plus | 表格、表单、卡片、标签、弹窗、分页等基础组件 |
| Apache ECharts | 设备状态和问题统计图表 |
| 原生 Fetch 封装 | 调用 FastAPI 接口 |
| pnpm | 前端依赖管理 |

本项目不引入 TanStack Query、Pinia 或其他复杂状态管理方案；页面之间通过路由参数和接口刷新保持必要的数据同步。

### 2.2 页面视觉方向

页面采用简洁的工业运维控制台风格：

- 深色蓝灰色作为主背景；
- 青色用于数据和正常信息；
- 绿色表示正常；
- 黄色表示预警；
- 红色表示故障或高风险；
- 使用等宽字体展示设备编号、运行指标和工作流 ID；
- 使用 Element Plus 组件保证开发效率，不自行重复实现基础表格和表单。

页面不追求复杂视觉动画，优先保证信息层次、状态区分和演示时的可读性。

## 3. 前端页面范围

### 3.1 总览页 `/overview`

作为系统首页，展示：

- 设备总数；
- 正常设备数；
- 预警设备数；
- 故障设备数；
- 待处理问题数；
- 近期维修草案；
- 设备状态统计图；
- 最近一次 Agent 工作流。

总览页不直接执行维修操作，只提供进入设备、问题、草案和工作流详情的入口。

### 3.2 设备页 `/devices`

展示设备列表，至少包含：

- 设备编号；
- 设备名称；
- 型号；
- 所属区域；
- 当前状态；
- 关键运行指标；
- 最近更新时间；
- 操作入口。

支持：

- 按名称、编号和状态筛选；
- 查看设备详情；
- 新增设备；
- 修改设备基本信息；
- 停用或归档模拟设备。

### 3.3 设备详情页 `/devices/:deviceId`

展示：

- 设备基本信息；
- 当前运行指标；
- 历史状态记录；
- 历史故障问题；
- 关联部件；
- 关联维修案例；
- 关联维修草案。

设备详情页提供“在 Hermes 中询问该设备”按钮，但不在本页面内实现聊天。

### 3.4 问题页 `/problems`

展示待处理和历史问题，至少包含：

- 问题编号；
- 关联设备；
- 故障现象；
- 严重程度；
- 当前处理状态；
- 发现时间；
- 数据来源；
- 关联维修草案。

支持：

- 新增问题；
- 修改问题描述；
- 修改问题状态；
- 调整严重程度；
- 归档问题；
- 查看关联设备和草案。

### 3.5 维修草案页 `/drafts`

展示 Hermes 生成的维修方案草案，至少包含：

- 草案编号；
- 关联设备；
- 故障判断；
- 风险等级；
- 草案状态；
- 生成时间；
- 是否需要人工确认。

支持按设备、状态和时间筛选，并进入草案详情。

### 3.6 维修草案详情页 `/drafts/:draftId`

展示：

- 故障判断；
- 可能原因；
- 检查步骤；
- 维修步骤；
- 所需工具和备件；
- 安全注意事项；
- 引用的知识图谱关系；
- 引用的维修案例或外部资料；
- 生成该草案的工作流。

支持：

- 修改草案状态；
- 标记为待人工确认；
- 标记为已确认；
- 归档草案。

不允许在前端直接修改 Agent 生成的完整维修步骤，避免把草案编辑功能扩展成复杂的文档编辑系统。

### 3.7 工作流页 `/workflows/:runId`

用于展示一次 Agent 处理任务的完整流程：

```text
用户问题
  ↓
识别设备和故障现象
  ↓
查询设备状态
  ↓
查询历史问题
  ↓
查询知识图谱和维修资料
  ↓
生成维修方案草案
  ↓
校验草案
  ↓
保存并展示结果
```

每个步骤至少展示：

- 步骤名称；
- 步骤状态；
- 开始和结束时间；
- 调用的工具名称；
- 工具结果摘要；
- 使用的证据；
- 错误或重试信息。

工作流页面是本项目体现“多工具调用”的核心页面。

### 3.8 Hermes 入口页 `/chat`

该页面不开发聊天组件，只展示：

- Hermes Agent 简介；
- 当前 Hermes 服务状态；
- 进入 Hermes Web UI 的按钮；
- 使用说明和示例问题。

Hermes Web UI 地址通过环境变量配置，例如：

```text
VITE_HERMES_WEB_URL=http://127.0.0.1:9119
```

`9119` 是 Hermes Web Dashboard，`8642` 是 Hermes API。入口页通过 FastAPI 的 `/api/hermes/health` 代理检查 Hermes 状态，浏览器不直接请求 8642。默认采用新页面或新标签页跳转，不实现 iframe 嵌入。

“配置 Provider API”按钮直接打开 Hermes Dashboard，由 Hermes 自身提供 Provider、模型和 API Key 配置能力。本项目不重复实现 API Key 表单，也不把 Provider 密钥保存到 SQLite。

### 3.9 外部资料页 `/materials`

展示和管理用户提供的真实运维资料，支持：

- 查看资料文件名、类型、来源说明、关联设备和参考状态；
- 导入 `md`、`txt`、`json`、`csv`、`pdf`、`docx` 文件；
- 为资料关联设备或设备型号；
- 标记资料是否允许 Agent 作为参考；
- 查看资料详情和可预览的文本内容；
- 删除资料记录。

资料导入仍由 FastAPI 负责校验和保存。前端不解析二进制文件，不执行上传内容，也不实现自动联网采集、自动知识抽取或向量检索。

## 4. FastAPI 接口范围

### 4.1 通用约定

所有接口返回 JSON，并统一包含必要的：

- `id`；
- `status`；
- `created_at`；
- `updated_at`；
- `source`。

接口需要提供基本的参数校验和错误响应，但不实现复杂权限校验。

### 4.2 总览和查询接口

```text
GET /api/dashboard/summary
GET /api/devices
GET /api/devices/{device_id}
GET /api/devices/{device_id}/statuses
GET /api/problems
GET /api/problems/{problem_id}
GET /api/drafts
GET /api/drafts/{draft_id}
GET /api/workflows/{run_id}
GET /api/materials
GET /api/health
GET /api/hermes/health
```

### 4.3 最低限度 CRUD 接口

#### 设备

```text
POST   /api/devices
PATCH  /api/devices/{device_id}
DELETE /api/devices/{device_id}
```

删除操作采用停用或归档方式，不直接物理删除具有关联记录的设备。

#### 问题

```text
POST   /api/problems
PATCH  /api/problems/{problem_id}
DELETE /api/problems/{problem_id}
```

问题删除采用归档方式，保留历史记录。

#### 维修草案

```text
POST   /api/drafts
PATCH  /api/drafts/{draft_id}/status
DELETE /api/drafts/{draft_id}
```

维修草案主要由 Agent 生成，前端只修改状态和归档，不直接修改完整维修内容。

#### 外部资料

```text
POST   /api/materials/import
DELETE /api/materials/{material_id}
```

资料导入接口只负责接收和保存外部资料及其元数据，不实现自动知识抽取。

### 4.4 Neo4j 查询接口

知识图谱查询不直接暴露给浏览器，可以通过 FastAPI 提供有限的只读接口：

```text
GET /api/knowledge/related
GET /api/knowledge/path
```

接口只返回经过整理的节点和关系，不返回 Neo4j 连接信息或数据库凭据。

## 5. 后端与前端异步行为

### 5.1 前端

前端使用 Fetch 封装完成异步请求，每个页面至少处理：

- 加载中状态；
- 请求成功状态；
- 空数据状态；
- 请求失败状态；
- 表单提交中状态；
- 提交成功提示；
- 提交失败提示。

不实现 WebSocket、SSE、复杂缓存和实时推送。

### 5.2 后端

FastAPI 接口使用异步接口处理 HTTP 请求和必要的数据库访问。SQLite 必须通过 SQLAlchemy 2.x Async ORM 和 `aiosqlite` 访问，使用 `AsyncEngine`、`async_sessionmaker` 和 `AsyncSession` 管理连接与会话。Neo4j 使用官方异步 Python Driver。

MCP 工具也支持异步调用，但不引入后台任务队列。MVP 只需要保证接口请求、数据库访问和工具调用不会因为不必要的同步 I/O 阻塞异步流程。

Agent 生成维修草案时，前端可以采用简单的“提交—等待—刷新”方式：

1. 用户从 Hermes 中提出问题；
2. Hermes 调用 MCP 工具并生成草案；
3. 后端保存草案和工作流记录；
4. 前端通过刷新或重新进入详情页查询结果。

## 6. Docker Compose 部署结构

最终 Demo 运行环境包含：

```text
hermes
neo4j
maintenance-service
frontend
```

其中 `maintenance-service` 可以同时提供：

- FastAPI HTTP 接口；
- FastMCP 服务入口；
- 共享业务逻辑；
- SQLite 数据文件访问；
- SQLAlchemy Async ORM 和 SQLite Session 管理；
- Neo4j 数据访问。

为了控制项目规模，MCP Server 和 FastAPI 暂不拆成两个独立容器。

推荐端口：

```text
frontend:            127.0.0.1:3000
maintenance-service: 127.0.0.1:8000
hermes:              127.0.0.1:8642
hermes dashboard:    127.0.0.1:9119
neo4j http:          127.0.0.1:7474
neo4j bolt:          127.0.0.1:7687
```

浏览器只访问 Frontend 和 FastAPI，不能直接访问 Neo4j，也不直接调用 MCP。

SQLite 数据文件应通过 Docker Volume 或项目本地数据目录保存，以便演示结束后可以整体清理。

### 7.1 后端测试

至少测试：

- 设备新增、查询、修改和停用；
- 问题新增、查询、状态修改和归档；
- 维修草案保存和状态修改；
- 外部资料导入；
- Neo4j 知识关系查询；
- MCP 工具输入输出；
- FastAPI 错误响应；

### 7.2 前端定向检查

本项目不额外建立 Vitest 或 Playwright 测试工程。交付前通过浏览器进行以下定向检查：

- 路由能够正常访问；
- 设备列表能够加载和筛选；
- 设备新增和修改表单能够提交；
- 问题状态能够修改；
- 草案详情能够展示证据和安全注意事项；
- 工作流时间线能够展示多步工具调用；
- 加载、空数据和错误状态能够显示；
- Hermes 入口能够正确跳转。
- Provider 配置按钮能够打开 Hermes Dashboard；
- 外部资料能够导入、查看详情和删除。

## 8. 最终演示验收标准

项目完成后，至少应能够现场演示以下内容：

1. 使用 Docker Compose 启动全部服务；
2. 打开 Vue 运维看板；
3. 查看工业空压机设备列表和运行状态；
4. 新增或修改一台模拟设备；
5. 查看一条设备故障问题；
6. 从前端进入 Hermes Dashboard，并配置 Provider API；
7. 提出一个空压机故障问题；
8. Hermes 调用多个 MCP 工具；
9. MCP 工具查询设备状态、故障记录、知识图谱和维修资料；
10. Hermes 生成维修方案草案；
11. 查看维修方案中的检查步骤、维修步骤、安全注意事项和证据；
12. 在前端查看本次工作流的工具调用时间线；
13. 修改草案或问题的状态；
14. 导入一份外部资料并查看其保存结果；
15. 使用 Docker Compose 清理项目服务和数据。

## 9. 明确不做的内容

为了保证项目能够在实习周期内完成，以下内容不纳入本项目：

- 真实设备或 PLC 接入；
- 实时传感器流；
- 高并发服务；
- 用户注册和复杂权限；
- 多租户；
- 复杂工单系统；
- 自动联网采集资料；
- 自动构建完整知识图谱；
- 向量数据库和语义检索平台；
- WebSocket 或流式工作流；
- 生产级日志、监控和告警平台；
- 修改 Hermes 源码；
- 独立开发聊天页面。

## 10. 本批次开发目标

完成批次三后，项目应具备以下明确目标：

1. 完成 Vue 工业运维看板；
2. 通过 Element Plus 快速实现基础页面和表单；
3. 展示设备、问题、维修草案和 Agent 工作流；
4. 提供设备、问题、草案和外部资料的最低限度 CRUD；
5. 保留 Hermes 对话能力，不重复开发聊天系统；
6. 通过 FastAPI 为前端提供统一 HTTP 接口；
7. 通过 Docker Compose 运行完整 Demo；
8. 完成一条可重复演示的多工具调用运维流程；
9. 能够在项目结束后一次性清理容器、卷、网络和演示数据。
