# 开发目标文档（批次二）：数据与知识图谱

## 1. 本批次结论

本项目使用“AI Mock 自建数据 + 可选外部资料导入”的数据方案。

MVP 阶段不连接真实工厂设备，不依赖实时传感器，也不实现自动互联网数据采集。系统通过预先生成的工业空压机模拟数据完成设备故障查询、知识检索和维修方案草案生成。

数据库采用轻量的双存储结构：

- SQLite：主业务数据库，负责设备、运行状态、故障记录、维修草案和工作流记录的 CRUD；
- Neo4j：知识图谱数据库，负责保存设备部件、故障现象、故障原因、维修措施、维修案例之间的关系。

SQLite 的后端连接和 CRUD 访问统一使用 SQLAlchemy 2.x Async ORM，并使用 `aiosqlite` 异步驱动。Neo4j 使用官方异步 Python Driver；不使用同步数据库驱动阻塞 FastAPI 或 MCP 的异步请求路径。

不引入 PostgreSQL 和 Redis。

这样既可以满足项目对 CRUD 的要求，也能保留知识图谱这一项目技术特色，同时避免把 MVP 做成复杂的生产级数据平台。

## 2. 数据来源

### 2.1 AI Mock 自建数据

项目主要使用 AI 辅助生成和人工审核后的模拟数据，包括：

- 工业空压机设备基本信息；
- 设备型号和部件信息；
- 设备运行状态；
- 压力、温度、振动、油位等模拟指标；
- 历史故障记录；
- 故障现象和故障原因；
- 维修案例；
- 维修步骤和 SOP；
- 安全注意事项；
- 维修方案草案样例。

AI 生成的数据必须经过基本人工检查，避免将明显不合理或具有安全风险的内容作为真实维修建议展示。

### 2.2 外部资料导入

系统只提供一个受控的外部资料导入接口，不实现自动爬虫、联网检索或复杂的文档管理系统。

外部资料接口用于允许用户提供：

- 设备说明书；
- 维修手册；
- 企业内部 SOP；
- 故障案例文档；
- 其他与设备维护相关的真实资料。

MVP 支持的资料形式暂定为：

- Markdown；
- TXT；
- JSON；
- CSV；
- PDF 或 DOCX（如果现有文档解析能力接入成本可控）。

资料导入后至少保存以下信息：

- 资料 ID；
- 文件名；
- 资料类型；
- 来源说明；
- 上传时间；
- 关联设备或设备型号；
- 原始内容或原始文件路径；
- 是否允许作为维修方案参考依据。

外部资料默认只作为参考信息，不自动覆盖已有知识图谱结论。

## 3. 数据库存储方案

### 3.1 SQLite：主业务数据库

SQLite 用于存储具有明确 CRUD 需求的业务数据：

- `devices`：设备信息；
- `device_statuses`：设备运行状态和模拟指标；
- `problems`：待处理问题和历史故障；
- `maintenance_drafts`：维修方案草案；
- `workflow_runs`：Agent 工作流记录；
- `workflow_steps`：工作流步骤和工具调用摘要；
- `external_materials`：外部资料元数据和内容索引；
- `audit_records`：必要的操作记录。

SQLite 的选择原因：

- 部署简单；
- 不需要单独启动数据库服务；
- 适合单人开发和本地演示；
- 支持基本事务和 CRUD；
- 数据文件便于备份、查看和一次性删除；
- 在本项目的低并发条件下足够使用。

### 3.1.1 SQLite 异步访问约束

SQLite 相关代码统一遵循以下方式：

- 使用 `create_async_engine("sqlite+aiosqlite:///...")` 创建异步引擎；
- 使用 `async_sessionmaker` 创建 `AsyncSession`；
- 在 FastAPI 请求和 MCP 工具中通过依赖或上下文管理器获取 Session；
- 使用 `await session.execute(...)`、`await session.commit()` 和 `await session.refresh(...)`；
- 一个请求或一个工具调用使用一个明确的 Session 生命周期；
- 不在路由中直接拼接 SQL 字符串；
- 不在异步请求路径中使用同步 `sqlite3` 或同步 SQLAlchemy Session。

MVP 阶段可以使用 SQLAlchemy `metadata.create_all` 完成初始化，不提前引入 Alembic。只有当数据库结构出现多次需要保留的版本迁移时，才考虑增加迁移工具。

### 3.2 Neo4j：知识图谱数据库

Neo4j 只承担知识图谱相关职责，不承担所有页面的普通 CRUD。

使用 Neo4j 的原因：

- 项目需要明确展示知识图谱技术；
- 故障现象、故障原因、部件、维修措施和维修案例之间具有明显的关联关系；
- 可以通过图查询展示故障诊断依据；
- 可以让 Hermes 通过 MCP 工具调用知识图谱查询。

MVP 阶段不要求 SQLite 和 Neo4j 完全实时同步。

推荐的处理方式是：

- SQLite 作为业务数据的主要来源；
- Neo4j 保存初始化的知识图谱和相对稳定的关系；
- 新增或修改设备时，先完成 SQLite CRUD；
- 只有当设备需要参与知识图谱查询时，才通过显式的同步函数补充 Neo4j 节点和关系；
- 不实现复杂的数据同步平台和双向一致性机制。

### 3.3 暂不使用的数据库和中间件

本项目暂不引入：

- PostgreSQL；
- MySQL；
- Redis；
- Kafka 或其他消息队列；
- Elasticsearch；
- 向量数据库；
- 独立对象存储。

如果后续出现以下情况，才考虑 PostgreSQL：

- 需要多人同时操作；
- 需要更复杂的事务和权限；
- 需要部署到远程服务器；
- SQLite 的并发写入成为实际问题。

当前项目不具备这些必要条件，因此不提前引入 PostgreSQL。

## 4. 数据模型范围

### 4.1 设备数据

设备至少包含：

- 设备 ID；
- 设备名称；
- 设备型号；
- 所属区域或产线；
- 当前状态；
- 最近更新时间；
- 额定压力；
- 额定功率；
- 投入使用时间。

设备状态至少包含：

- 运行状态；
- 排气压力；
- 温度；
- 振动值；
- 油位状态；
- 采集时间；
- 状态来源。

### 4.2 故障和问题数据

问题记录至少包含：

- 问题 ID；
- 关联设备 ID；
- 故障现象；
- 严重程度；
- 当前状态；
- 发现时间；
- 问题描述；
- 可能原因；
- 数据来源；
- 关联维修草案 ID。

### 4.3 维修方案草案

维修方案草案至少包含：

- 草案 ID；
- 关联设备；
- 关联问题；
- 故障判断；
- 可能原因；
- 检查步骤；
- 维修步骤；
- 所需工具和备件；
- 安全注意事项；
- 引用的知识和案例；
- 生成时间；
- 草案状态；
- 是否需要人工确认。

草案只能作为辅助决策参考，不表示系统已经确认故障，也不表示可以跳过人工安全检查。

## 5. 知识图谱设计

### 5.1 节点类型

MVP 只实现以下节点类型：

- `Device`：设备；
- `DeviceModel`：设备型号；
- `Component`：部件；
- `FaultSymptom`：故障现象；
- `FaultCause`：故障原因；
- `MaintenanceAction`：维修措施；
- `MaintenanceCase`：维修案例；
- `SOP`：标准操作流程；
- `SafetyNotice`：安全注意事项。

### 5.2 关系类型

MVP 只实现必要关系：

- `Device -[:INSTANCE_OF]-> DeviceModel`；
- `Device -[:CONTAINS]-> Component`；
- `FaultSymptom -[:MAY_BE_CAUSED_BY]-> FaultCause`；
- `FaultCause -[:SOLVED_BY]-> MaintenanceAction`；
- `MaintenanceAction -[:REFER_TO]-> SOP`；
- `MaintenanceCase -[:APPLIES_TO]-> DeviceModel`；
- `MaintenanceCase -[:ADDRESSES]-> FaultSymptom`；
- `MaintenanceAction -[:REQUIRES]-> SafetyNotice`。

### 5.3 图谱使用范围

知识图谱主要用于：

- 根据故障现象查找可能原因；
- 根据故障原因查找维修措施；
- 查找适用于当前设备型号的维修案例；
- 查找维修措施对应的 SOP 和安全注意事项；
- 为维修方案草案提供可展示的证据链。

不实现：

- 自动从任意文档中抽取完整知识图谱；
- 复杂的知识推理算法；
- 图神经网络；
- 机器学习故障预测；
- 自动替代专业维修人员进行最终诊断。

## 6. 数据 CRUD 能力

项目需要实现有限但可演示的 CRUD 能力。

### 6.1 设备

支持：

- 新增设备；
- 查询设备列表；
- 查询设备详情；
- 修改设备基本信息；
- 删除或停用模拟设备。

### 6.2 问题和故障

支持：

- 新增故障问题；
- 查询问题列表；
- 修改问题状态；
- 关联设备和维修草案；
- 查看历史故障。

### 6.3 维修草案

支持：

- 由 Agent 生成维修草案；
- 查询草案列表；
- 查看草案详情；
- 修改草案状态；
- 标记为“待人工确认”“已确认”或“已归档”。

### 6.4 知识图谱

知识图谱以初始化和查询为主，MVP 不开发复杂的图谱管理后台。

可以提供简单的：

- 新增知识节点；
- 新增知识关系；
- 查询相关节点和关系；
- 删除明显错误的模拟关系。

知识图谱的编辑接口只用于演示和数据维护，不作为主要业务流程。

## 7. MCP 工具范围

为了控制项目规模，MVP 只实现以下工具：

1. `list_devices`：查询设备列表；
2. `get_device_status`：查询指定设备当前状态；
3. `search_problems`：查询设备故障和问题；
4. `search_knowledge`：根据设备、故障现象或关键词查询知识图谱；
5. `get_maintenance_material`：查询 SOP、维修案例和外部资料；
6. `create_repair_draft`：根据查询结果生成维修方案草案；
7. `validate_repair_draft`：检查草案是否缺少步骤、安全说明或证据；
8. `record_workflow_run`：保存 Agent 工作流记录。

不额外实现大量细粒度工具。一个工具只有在能够支撑演示流程或明确体现多工具调用时才保留。

## 8. 推荐的 Agent 工作流

MVP 的完整工作流为：

```text
用户提出空压机故障问题
        ↓
查询设备和当前运行状态
        ↓
查询历史问题和故障记录
        ↓
查询知识图谱中的故障原因、维修措施和案例
        ↓
查询 SOP、安全注意事项和外部资料
        ↓
生成维修方案草案
        ↓
校验草案完整性
        ↓
保存工作流和草案
        ↓
前端展示结果，等待人工确认
```

该流程用于演示 Agent 的工具调用能力，不要求实现复杂的自动规划算法。可以通过 Hermes 的系统提示词和工具描述，引导 Agent 按照这一流程调用工具。

## 9. 外部资料接口

系统预留一个外部资料导入接口：

```text
POST /api/materials/import
```

该接口至少支持：

- 上传资料；
- 保存资料元数据；
- 关联设备或设备型号；
- 标记资料来源；
- 标记是否允许作为维修参考。

MVP 阶段不要求：

- 自动联网下载资料；
- 自动判断资料可信度；
- 自动把全文转换为完整知识图谱；
- 实现复杂的全文检索或向量检索。

如果时间允许，可以增加基于关键词的简单资料搜索；否则只需要完成资料保存和后续查询接口预留。

## 10. 本批次开发目标

完成批次二后，项目应达到以下目标：

1. 明确使用 AI Mock 数据作为主要数据来源；
2. 明确支持外部真实资料导入，但不实现自动采集；
3. 明确使用 SQLite 完成主业务数据 CRUD；
4. 保留 Neo4j 用于知识图谱查询和关系展示；
5. 不引入 PostgreSQL、Redis 和向量数据库；
6. 建立工业空压机的最小知识图谱；
7. 实现数量受控的 MCP 工具；
8. 支持新增设备、修改问题状态和查看维修草案；
9. 完成一次“查询设备—查询故障—查询知识—生成草案—保存记录”的 Agent 工作流设计。

## 11. 范围控制原则

后续开发中遵循以下原则：

- 优先完成可运行的完整闭环；
- 优先使用明确的模拟数据；
- 优先实现查询和展示，再实现编辑；
- 优先实现少量有代表性的工具；
- 不为未来可能的生产化需求提前设计复杂架构；
- 不为了体现技术名词而增加无实际演示价值的功能。
