# 后续功能补充说明

## 1. 文档定位

本文档用于记录现有三批次开发目标之外，项目后续需要补齐或优化的功能。

项目仍然定位为本地运行的生产实习演示 Demo。后续功能以补齐演示闭环为目标，不扩展为高并发、生产级或完整工业知识管理系统。

## 2. 待补充功能总览

| 优先级 | 功能                   | 目标                                                   |
| ------ | ---------------------- | ------------------------------------------------------ |
| P0     | Neo4j 知识图谱初始化   | 确保启动项目后知识图谱不是空数据                       |
| P0     | 知识图谱前端查看页面   | 让用户可以直接查看设备、故障、原因和维修动作之间的关系 |
| P1     | 设备详情与知识图谱联动 | 从设备详情快速进入对应的图谱查询结果                   |
| P1     | Agent 设备确认安全门禁 | 防止 Agent 在设备查询失败时猜测设备并生成错误草案      |
| P1     | 知识图谱接口响应模型   | 统一后端和前端使用的数据结构                           |
| P2     | 维修草案审核与反馈     | 支持用户确认、驳回或修订维修草案，形成演示闭环增强     |

## 3. P0：Neo4j 知识图谱初始化

### 3.1 功能目标

将知识图谱的 AI Mock 种子数据接入 Docker Compose 启动流程，保证项目启动后可以直接进行知识查询和前端图谱展示。

### 3.2 实现要求

- 将现有 `initialize_knowledge_graph()` 接入项目初始化流程，或提供明确的独立初始化命令。
- 初始化过程必须支持重复执行，不能产生重复节点和关系。
- 初始化过程不能删除或覆盖用户后续维护的数据。
- 至少初始化设备型号、故障现象、故障原因、维修动作、历史案例和安全要求等演示数据。
- 初始化完成后，Neo4j 中应存在非空的节点和关系。
- MCP 知识查询工具应能读取初始化后的图谱数据。

### 3.3 验收方式

启动 Docker Compose 后，通过知识查询接口或 MCP 工具进行一次设备型号查询，能够返回匹配结果、案例或证据链，而不是空结果。

## 4. P0：知识图谱前端查看页面

### 4.1 页面入口

- 新增前端路由：`/knowledge`。
- 在系统侧边栏增加“知识图谱”菜单项。
- 页面可以从设备详情页跳转，也可以独立打开并通过关键词查询。

### 4.2 页面功能

用户可以输入设备型号、设备名称或故障关键词，页面展示：

- 设备或设备型号节点；
- 故障现象节点；
- 故障原因节点；
- 维修动作节点；
- 历史案例节点；
- SOP、安全要求或维修注意事项节点；
- 节点之间的关系方向和关系名称；
- 当前节点的属性、来源和证据说明。

### 4.3 技术要求

- 使用现有 Vue 3、TypeScript、Element Plus 和 ECharts。
- 优先复用现有 `/api/knowledge/related` 和 `/api/knowledge/path` 接口。
- 不额外引入专用图数据库前端框架。
- 处理加载中、无数据、接口失败和 Neo4j 不可用等状态。
- 本功能只要求只读展示，不要求在页面上编辑图谱。

## 5. P1：设备详情与知识图谱联动

在 `/devices/:deviceId` 页面增加“查看关联知识图谱”入口，跳转到 `/knowledge` 时携带设备型号或关键词。

后续实现时，需要检查真实后端适配逻辑，补齐设备详情中的关联组件、历史案例等字段，避免长期返回空数组占位。图谱页面仍应支持脱离设备详情独立查询。

## 6. P1：Agent 设备确认安全门禁

### 6.1 问题背景

当设备查询失败、设备不存在或 MCP 服务不可用时，Agent 不应继续猜测 `device_id` 并生成维修方案。维修方案必须建立在明确的设备和知识查询结果之上。

### 6.2 实现要求

- 调用 `create_repair_draft` 前，必须存在成功的设备查询结果。
- 禁止使用猜测或硬编码的 `device_id` 创建草案。
- 校验 `device_id` 与设备编码、设备名称或设备型号的一致性。
- 设备查询失败、设备不存在或知识查询失败时，停止生成草案，或将流程标记为 `needs_input` / 失败。
- 前端将此类结果展示为“需要补充信息”或“查询失败”，不展示依据不足的完整维修方案。

## 7. P1：知识图谱接口响应模型

在 `services/maintenance_service/app/schemas/knowledge.py` 中补充当前演示所需的 Pydantic 模型，至少覆盖：

- 图谱节点；
- 图谱关系；
- 关联查询结果；
- 路径查询结果；
- 历史案例；
- 证据和来源信息。

FastAPI、FastMCP 和 Vue 前端应基于统一字段进行数据传递。模型保持简单，不提前增加复杂本体管理、版本管理或权限模型。

## 8. P2：推荐新增功能——维修草案审核与反馈

知识图谱页面和 Agent 安全门禁完成后，推荐增加“维修草案审核与反馈”功能：

- 用户可以将草案标记为“待审核”“已确认”或“已驳回”；
- 用户可以填写简短的修改意见；
- 前端展示草案当前审核状态和最近一次修改意见；
- 审核结果作为演示记录保存，不直接控制真实设备；
- 后续可以将用户确认或驳回结果作为 mock 数据改进的参考。

该功能可以复用现有维修草案 CRUD，不需要引入新的数据库、消息队列或复杂权限系统。

## 9. 后续验收补充

完成本文档中的 P0/P1 功能后，应能够完成以下演示：

1. 启动 Docker Compose，Neo4j 自动完成幂等初始化；
2. 在前端打开“知识图谱”页面并查询设备型号；
3. 查看节点、关系、案例和证据链；
4. 从设备详情跳转到对应的知识图谱；
5. 通过 Hermes 对话完成设备查询、知识查询和维修草案生成；
6. 在设备查询失败时，Agent 不生成绑定错误设备的维修草案；
7. 在前端查看工作流和维修草案结果。

本轮后续开发不新增独立 Vitest 或 Playwright 测试，使用现有后端测试、前端构建检查和人工浏览器冒烟测试完成验证。

## 10. 暂不纳入范围

以下内容继续不属于本项目 MVP 必做范围：

- 图谱完整编辑后台；
- 自动从外部资料抽取完整知识图谱；
- 向量数据库和复杂语义检索；
- 真实设备、PLC 或传感器接入；
- 生产级权限、审计、监控和高并发优化；
- 修改 Hermes 源码或重新实现 Hermes 对话页面。
