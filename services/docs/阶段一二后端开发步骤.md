# 阶段一、阶段二后端开发步骤

> 当前进度：步骤一、步骤二已完成，步骤三待开始。

## 1. 文档定位

本文档用于拆分阶段一、阶段二的后端与 Agent 开发任务，作为后续分步开发和验收的执行清单。

本项目是工业空压机运维 Demo，目标是完成：

```text
Mock 数据初始化
    ↓
SQLite CRUD 与 Neo4j 知识查询
    ↓
FastAPI HTTP 接口与 FastMCP 工具
    ↓
Hermes 多工具调用
    ↓
维修方案草案生成、校验和工作流记录
```

本轮不实现 Vue 页面，不修改 Hermes 源码，不接入真实工业设备，也不实现真实设备控制。

## 2. 前置工作

以下内容已完成，不计入后续 8 步：

- 使用根目录 `.venv` 和 `uv` 管理 Python 依赖；
- 引入 FastAPI、Uvicorn、FastMCP、SQLAlchemy Async、aiosqlite、Neo4j Async Driver、Pydantic Settings、python-multipart 和 MarkItDown；
- 引入 pytest、pytest-asyncio、httpx 和 Ruff 开发依赖；
- 建立 `services/maintenance_service/` 独立后端目录；
- 建立 FastAPI 入口、FastMCP 入口、配置模块、SQLite Session、Neo4j 客户端和基础测试；
- 实现并验证 `/api/health` 健康检查；
- 保留现有 Hermes、Neo4j Compose 配置不变。

## 3. 分步开发计划

### 第 1 步：SQLite 数据契约与模型（已完成）

#### 实现范围

- 完成 `Device`、`DeviceStatus`、`Problem`、`MaintenanceDraft`、`WorkflowRun`、`WorkflowStep`、`ExternalMaterial`、`AuditRecord` 模型；
- 确定主键、外键、时间字段、来源字段和归档字段；
- 确定设备、问题、草案和工作流的状态值；
- 确定维修草案中的数组型字段和证据字段格式；
- 完善 `AsyncEngine`、`async_sessionmaker`、`AsyncSession` 和建表入口；
- 不引入 Alembic，MVP 使用 `Base.metadata.create_all` 初始化表结构。

#### 边界

本步只建立数据结构和数据库生命周期，不实现 HTTP CRUD、Neo4j 查询或 MCP 工具。

#### 完成标准

- 所有模型能够被异步 SQLAlchemy 正确导入；
- SQLite 能够重复执行建表初始化；
- 模型字段和状态值有对应测试；
- 现有 `/api/health` 和启动骨架继续通过测试。

### 第 2 步：Mock 数据、初始化和仓储服务（已完成）

#### 实现范围

- 准备 5—8 台空压机、当前状态、历史问题、维修案例和 SOP Mock 数据；
- 将初始化数据保存为 JSON、CSV 或 Markdown 等可审阅文件；
- 实现 SQLite 初始化和 Mock 数据导入脚本；
- 保证重复执行不会无控制地创建重复数据；
- 实现设备、状态、问题、草案、资料和工作流 Repository；
- 在 `domain/services.py` 中封装 FastAPI 与 FastMCP 共用的业务查询和写入逻辑。

#### 边界

本步不新增正式 HTTP 路由和 MCP 工具，但 Repository 和 domain 服务的接口需要为后续两类入口稳定复用。

#### 完成标准

- 初始化脚本至少覆盖排气压力异常、温度过高、振动异常或润滑不足三个演示故障；
- 重复执行初始化后数据数量和业务 ID 保持稳定；
- Repository 的增删改查和归档行为有单元测试；
- 数据库异常不会留下未提交事务。

### 第 3 步：设备与问题 FastAPI API

#### 实现范围

实现以下接口：

```text
GET    /api/devices
GET    /api/devices/{device_id}
POST   /api/devices
PATCH  /api/devices/{device_id}
DELETE /api/devices/{device_id}
GET    /api/devices/{device_id}/statuses

GET    /api/problems
GET    /api/problems/{problem_id}
POST   /api/problems
PATCH  /api/problems/{problem_id}
DELETE /api/problems/{problem_id}
```

#### 边界

- 路由处理器保持轻量，只负责参数校验、Session 获取和响应转换；
- 设备和问题的具体业务逻辑调用第 2 步的 domain 服务；
- 删除设备和问题采用归档或停用，不物理删除关联历史。

#### 完成标准

- 请求和响应均使用 Pydantic Schema；
- 不存在资源、非法状态、非法参数均返回明确错误响应；
- 设备新增、查询、修改、归档和状态查询可通过接口测试验证；
- 问题新增、查询、状态修改和归档可通过接口测试验证。

### 第 4 步：草案、工作流、资料和总览 API

#### 实现范围

实现以下接口：

```text
GET    /api/drafts
GET    /api/drafts/{draft_id}
POST   /api/drafts
PATCH  /api/drafts/{draft_id}/status
DELETE /api/drafts/{draft_id}
GET    /api/workflows/{run_id}

GET    /api/materials
POST   /api/materials/import
DELETE /api/materials/{material_id}

GET    /api/dashboard/summary
```

#### 边界

- 草案允许通过 API 保存测试数据，但自动生成留到阶段二 MCP 工具；
- 外部资料只做受控保存和元数据管理，不自动爬取或自动抽取知识；
- 上传资料不得执行，且必须阻止路径穿越。

#### 完成标准

- 草案包含诊断、可能原因、检查步骤、维修步骤、工具、备件、安全事项、证据和人工确认标记；
- 文件类型、文件大小、文件名、保存路径和关联设备均经过校验；
- 工作流详情能够返回运行状态和步骤摘要；
- Dashboard 能返回设备、问题、草案等基础统计。

### 第 5 步：Neo4j 知识图谱

#### 实现范围

- 实现 Neo4j 官方异步 Driver 生命周期；
- 初始化 `Device`、`DeviceModel`、`Component`、`FaultSymptom`、`FaultCause`、`MaintenanceAction`、`MaintenanceCase`、`SOP`、`SafetyNotice` 节点；
- 初始化 `INSTANCE_OF`、`CONTAINS`、`MAY_BE_CAUSED_BY`、`SOLVED_BY`、`REFER_TO`、`APPLIES_TO`、`ADDRESSES`、`REQUIRES` 关系；
- 实现幂等的节点和关系初始化；
- 实现按设备、型号、故障现象和关键词查询证据链。

#### 边界

- Neo4j 只负责知识图谱，不替代 SQLite 业务 CRUD；
- 只使用参数化 Cypher；
- 不实现复杂推理、自动文档抽取、机器学习预测和双向实时同步。

#### 完成标准

- Neo4j 初始化脚本重复执行不会产生重复节点和关系；
- 至少一个故障现象能够查询到原因、维修措施、SOP 和安全事项；
- Neo4j 不可用时，后端返回受控错误，不暴露堆栈和凭据；
- 图查询结果能够整理为后续 API 和 MCP 可复用的结构。

### 第 6 步：MCP 只读工具

#### 实现范围

实现以下 FastMCP 工具：

1. `list_devices`
2. `get_device_status`
3. `search_problems`
4. `search_knowledge`
5. `get_maintenance_material`

#### 边界

- 工具只调用共享 domain 服务和 graph 查询模块；
- 工具不直接拼接 SQL/Cypher，不重复实现 Repository 查询；
- 每个工具明确中文说明、输入参数、返回结构、错误行为和数据来源。

#### 完成标准

- 正常输入和错误输入均有测试；
- 设备、状态、故障、知识和资料结果能够被 Hermes 继续使用；
- 查询为空时返回明确的空结果和不确定性信息，不编造证据。

### 第 7 步：MCP 草案与工作流工具

#### 实现范围

实现以下 FastMCP 工具：

6. `create_repair_draft`
7. `validate_repair_draft`
8. `record_workflow_run`

#### 边界

- `create_repair_draft` 只生成和保存维修方案草案，不执行真实维修或设备控制；
- `validate_repair_draft` 只做结构完整性和安全提示检查；
- 工作流只保存展示所需的摘要、证据引用、状态和错误信息，不保存不必要的敏感原文。

#### 完成标准

- 草案可以保存到 SQLite 并被 API 查询；
- 缺少设备、故障判断、检查步骤、安全事项或证据时，校验返回问题清单；
- 工具调用失败、无数据和校验失败均能记录为工作流步骤；
- 草案默认标记为需要人工确认。

### 第 8 步：Hermes 配置与完整联调

#### 实现范围

- 配置 Hermes 连接 FastMCP 服务；
- 通过环境变量管理 MCP 地址和认证信息；
- 编写工业空压机 Demo 专用系统提示词；
- 明确草案必须人工确认、缺少数据时需要追问、无证据时不得编造；
- 在 Compose 中加入 maintenance-service 服务；
- 完成阶段一、二完整演示流程和联调测试。

#### 推荐验证流程

```text
识别设备
  ↓
list_devices / get_device_status
  ↓
search_problems
  ↓
search_knowledge
  ↓
get_maintenance_material
  ↓
create_repair_draft
  ↓
validate_repair_draft
  ↓
record_workflow_run
```

#### 完成标准

使用类似以下问题能够完成可重复演示：

```text
空压机 AC-001 当前温度过高，请分析可能原因并给出维修建议。
```

系统需要能够查询设备状态、历史问题、Neo4j 知识、维修资料，生成并校验维修草案，保存草案和工作流记录，并返回证据、安全注意事项和人工确认提示。

## 4. 防止破坏性重构的开发约束

- 第 1 步冻结核心模型字段、状态值、ID 类型和草案 JSON 结构，后续优先向后兼容；
- 第 2 步建立 Repository 和 domain 服务后，FastAPI 与 FastMCP 不再直接编写重复数据库逻辑；
- 后续步骤只新增路由、工具和服务，不移动或重命名现有 `app/main.py`、`app/config.py`、`app/db/session.py` 和 `app/mcp_server.py`；
- Neo4j 访问始终隔离在 `app/graph/`，不把图查询逻辑混入 SQLite Repository；
- 每一步必须先补对应测试，再进入下一步；
- 每一步完成后保留并运行全部历史测试；
- 不提前引入 PostgreSQL、Redis、消息队列、向量数据库、迁移系统或复杂任务调度器；
- 维修方案始终是草案，任何工具都不得控制真实设备。

## 5. 每步通用验收要求

每个步骤结束时至少执行：

```powershell
uv run pytest -p no:cacheprovider
uv run ruff check services
```

涉及依赖或 Compose 的步骤，还需要执行：

```powershell
uv lock --check
docker compose -f compose.yml config --quiet
```
